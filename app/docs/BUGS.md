# Каталог дефектов Django-версии

Результат построчного разбора `src/apps/mail`, `src/apps/useraccount` и
`src/_project`. Для каждого дефекта указано: где он живёт, что видит
пользователь, и как он устранён в новой реализации.

Ссылки на строки — по состоянию кода на коммите `b3e1c5d`.

Колонка «Тест» — имя теста, который воспроизводит дефект. Тесты помечены
меткой `regression`, прогоняются командой:

```bash
pytest -m regression
```

---

## Критические

Приводят к потере данных, повторной рассылке или утечке учётных данных.

### 1. Двойная рассылка из-за гонки при захвате кампании

**Где:** `views.py:627-659`, `check_mass_mail_campaigns.py:445-456`

Проверка «кампания уже отправляется?» и установка статуса `sending` —
два отдельных запроса. Между ними есть промежуток, в который успевает
войти второй исполнитель:

```python
if campaign.status == 'sending':        # запрос 1
    return ...
campaign.status = 'scheduled'            # запрос 2
campaign.save(...)
run_send_campaign_now.delay(campaign.id, force=True)
```

**Что видит пользователь:** получатели получают письмо дважды. Срабатывает при
двойном клике на «Отправить сейчас», повторной доставке задачи Celery (штатное
поведение брокера при таймауте подтверждения) и при наложении расписания на
ручной запуск.

**Исправление:** захват одним атомарным `UPDATE ... WHERE status != 'sending'
RETURNING id`. Кто изменил строку — тот и отправляет; остальные получают ноль
строк и выходят. `campaign_sender._acquire`.

**Тест:** `test_second_concurrent_run_is_rejected`

---

### 2. Вложения к письмам не прикреплялись никогда

**Где:** `signals.py:428` в связке с `views.py:1087-1104`

Сигнал `post_save` отправляет письмо в момент `Message.objects.create(...)`.
Файлы же создаются в цикле **после** этого вызова:

```python
new_message = Message.objects.create(...)   # ← здесь сигнал уже отправил письмо
for file in files:
    MessageFile.objects.create(file=file, message=new_message)
```

На момент `instance.files.exists()` связанных файлов ещё нет.

**Что видит пользователь:** прикрепляет документ, интерфейс подтверждает
отправку, получатель получает письмо без вложения.

**Исправление:** отправка вынесена из сигналов в явный сервис, вызываемый после
полной сборки сообщения вместе с вложениями. Сигналов в новой версии нет вообще.

---

### 3. Пароли SMTP попадают в логи

**Где:** `services.py:38`, `signals.py:138` — `server.set_debuglevel(2)`;
`signals.py:152-154` — печать первых символов пароля

`set_debuglevel(2)` выводит весь SMTP-диалог, включая строку `AUTH PLAIN
<base64>`, где base64 тривиально декодируется в логин и пароль. Логи Celery
пишутся в `_logs/` и попадают в любую выгрузку.

**Исправление:** отладочный режим SMTP убран; текст ошибок сервера проходит
через `_describe()`, который вырезает строки `AUTH`. `smtp/sender.py`.

---

### 4. CSRF-защита отключена на операциях, изменяющих данные

**Где:** `views.py:1122, 1154, 1176, 1238, 1257, 1307, 1335, 1484`

`@method_decorator(csrf_exempt)` стоит на удалении, восстановлении,
перемещении сообщений, создании директорий и загрузке файлов.

**Что это даёт атакующему:** страница на стороннем сайте, открытая
авторизованным пользователем, может удалить его переписку — браузер отправит
cookie сессии автоматически.

**Исправление:** CSRF обязателен для всех небезопасных методов; токен привязан
к сессии, поэтому не переносится между пользователями. `core/security.py`.

---

### 5. Доступ к чужим сообщениям через подстроку в адресе

**Где:** `views.py:1129, 1161, 1184, 1245, 1264, 1342` и др.

Проверка прав построена на `icontains`:

```python
Q(clients__icontains=request.user.email)
```

Это поиск подстроки. Пользователь `a@b.ru` проходит проверку для сообщения,
адресованного `xa@b.ru` или `a@b.ru.evil.com`.

**Что видит пользователь:** чужие письма в своей переписке; при неудачном
совпадении адресов — возможность удалить чужое сообщение.

**Исправление:** принадлежность определяется точным совпадением нормализованного
адреса, а не подстрокой. `domain/emails.normalize_email` + явная проверка
владельца в сервисном слое.

**Тест:** `test_excludes_case_insensitively`, `test_at_sign_alone_is_not_an_email`

---

### 6. Шаблоны писем общие для всех пользователей

**Где:** `views.py:168-221`, `views.py:563-585`

`MessageTemplates` не имеет поля владельца, а вьюхи ограничены только
`LoginRequiredMixin`. Любой пользователь видит, редактирует, копирует и
удаляет шаблоны всех остальных.

**Исправление:** шаблоны ограничены владельцем на уровне репозитория;
операции чтения и записи проверяют `user_id`. Требует аддитивной миграции
(добавление колонки владельца) — описано в `docs/MIGRATION.md`.

---

### 7. Гонка при генерации номера сообщения

**Где:** `models.py:222-271`

Номер вида `01-0001` вычисляется чтением максимума и увеличением на единицу,
без блокировки и без уникального ограничения на уровне транзакции. Два
одновременных сообщения получают один номер → `IntegrityError` (поле
`custom_id` уникально) → 500 у пользователя.

Дополнительно: **вся таблица сообщений с данным префиксом загружается в
память** для поиска максимума:

```python
messages = Message.objects.filter(custom_id__startswith=prefix)
for msg in messages:            # ← O(n) по всем сообщениям
    num_part = msg.custom_id.split('-')[1]
```

При 100 000 сообщений каждая отправка письма читает 100 000 строк.

**Исправление:** номер выдаётся последовательностью БД; поиск максимума —
агрегатным запросом, а не в Python.

---

### 8. Пароли SMTP хранятся открытым текстом

**Где:** `models.py:478` — `email_host_password = models.TextField(...)`

Пароли от почтовых ящиков клиентов лежат в БД без шифрования. Дамп базы =
компрометация всех почтовых ящиков.

**Исправление:** поле шифруется симметричным ключом приложения при записи и
расшифровывается только в момент подключения. Ключ хранится вне БД.
Требует миграции данных — описано в `docs/MIGRATION.md`.

## Высокие

Ломают основной сценарий или искажают данные.

### 9. Отправка письма выполняется внутри HTTP-запроса

**Где:** `signals.py:345-459`

Сигнал `post_save` синхронно подключается к SMTP, авторизуется и отправляет.
При недоступном сервере запрос висит до таймаута (30 с × 2 подключения).

**Исправление:** отправка выполняется фоновой задачей; HTTP-обработчик только
ставит её в очередь.

---

### 10. Ошибки отправки поглощаются, пользователь видит «успех»

**Где:** `signals.py:452-457`, `views.py:1106-1110`

Исключение в сигнале перехватывается и печатается в stdout. Вьюха уже вернула
`{'status': 'success', 'message': 'Сообщение отправлено'}`.

**Что видит пользователь:** «Сообщение отправлено» при том, что письмо не ушло.
Узнать об этом невозможно — в интерфейсе нет следов ошибки.

**Исправление:** результат отправки фиксируется в логе и отражается в статусе
сообщения; ошибки не поглощаются.

---

### 11. Дубли в списке получателей → два письма одному адресату

**Где:** `models.py:644-654` — `get_recipients_list()` не дедуплицирует

**Исправление:** `domain/emails.parse_emails` дедуплицирует по нормализованной
форме, сохраняя порядок.

**Тест:** `test_duplicate_recipients_get_one_email`

---

### 12. Стоп-лист регистрозависим при добавлении, но не при фильтрации

**Где:** `models.py:534-542` (добавление — точное сравнение) против
`check_mass_mail_campaigns.py:542-547` (фильтрация — через `lower()`)

**Что видит пользователь:** отписавшийся `Ivan@Mail.ru` добавляется в стоп-лист
повторно при каждом клике (дубли в списке), а `IVAN@MAIL.RU` в списке не
блокирует `ivan@mail.ru` при добавлении.

**Исправление:** единая нормализация во всех операциях.

**Тест:** `test_stoplist_is_case_insensitive`

---

### 13. Повторная отправка при возобновлении из-за регистра

**Где:** `check_mass_mail_campaigns.py:555-561`

Уже отправленные адреса вычитаются точным совпадением, тогда как стоп-лист —
регистронезависимо. Адрес, записанный в лог в другом регистре, получает
письмо повторно.

**Тест:** `test_resume_matches_already_sent_case_insensitively`

---

### 14. Порядок получателей теряется

**Где:** `models.py:673-676`

```python
updated_recipients = current_recipients - set(emails_to_move)
self.recipient_emails = ', '.join(updated_recipients)
```

`set` не сохраняет порядок, причём порядок обхода меняется между запусками
процесса. Возобновление рассылки идёт не с того места.

**Тест:** `test_join_is_order_stable`

---

### 15. Расписание стирается при временной ошибке SMTP

**Где:** `check_mass_mail_campaigns.py:780-782`

```python
campaign.status = 'draft'
campaign.scheduled_time = None      # ← время, назначенное пользователем, потеряно
```

При кратковременной недоступности почтового сервера пользователь молча теряет
настроенное время отправки.

**Исправление:** `_abort` меняет только статус, расписание сохраняется.

**Тест:** `test_campaign_without_recipients_returns_to_draft_keeping_schedule`

---

### 16. Двойное SMTP-подключение на каждое письмо

**Где:** `signals.py:196-202`, `check_mass_mail_campaigns.py:628-633`

Перед отправкой выполняется полноценный «тестовый» коннект с авторизацией,
затем открывается второе, рабочее соединение.

**Что видит пользователь:** рассылка идёт вдвое дольше; провайдеры (Яндекс,
Mail.ru) временно блокируют ящик за слишком частые авторизации.

**Исправление:** одно соединение на пачку писем, проверка подключения — только
по явной кнопке.

**Тест:** `test_uses_single_connection_per_batch`

---

### 17. Обрыв связи помечает неудачными адреса, которым не пытались отправить

**Где:** `check_mass_mail_campaigns.py:351-363`

При исключении на уровне соединения весь остаток пачки записывается как
`failed`. Эти адреса исключаются из повторной отправки, хотя письма им никогда
не уходили.

**Тест:** `test_connection_loss_does_not_mark_whole_batch_failed`

---

### 18. Счётчики обновляются неатомарно

**Где:** `check_mass_mail_campaigns.py:302, 321`

```python
campaign.sent_count += 1                      # в памяти
campaign.save(update_fields=['sent_count'])   # перезапись целиком
```

Параллельное изменение (сброс счётчиков из интерфейса, второй воркер) затирается.

**Исправление:** `UPDATE ... SET sent_count = sent_count + 1` на стороне БД.

---

### 19. Запись в базу при GET-запросе

**Где:** `views.py:876-887`

Открытие списка сообщений выполняет до 200 `UPDATE`. GET обязан быть
идемпотентным: повторное открытие страницы, префетч браузера или обход
поисковым роботом меняют данные.

**Исправление:** тип сообщения вычисляется при записи, а не при чтении.

---

### 20. `time.sleep` блокирует единственный воркер

**Где:** `check_mass_mail_campaigns.py:347, 709`; `docker-compose.yaml:70`
(`--concurrency=1`)

Кампания на 1000 писем с интервалом 10 секунд занимает воркер на 2,7 часа.
Всё это время не выполняется ничего другого — включая проверку входящей почты
и другие рассылки.

**Исправление:** пауза реализована как отложенный повтор задачи, а не как
блокирующий сон; воркер свободен между письмами.

## Средние

### 21. Мусорные данные при первом запуске

`views.py:49-52` — стоп-лист создаётся с содержимым
`'mail@na.ru, mail2@na.ru'`. Тестовые адреса попадают в боевой стоп-лист.

### 22. `500` при открытии шаблона без даты

`views.py:573-574` — `template.created_at.strftime(...)` при
`created_at = None` (поле объявлено `null=True`).

### 23. `500` на некорректном JSON

`views.py:142, 158` — `json.loads(request.body)` без обработки ошибки.

### 24. Вход падает при дублирующемся email

`useraccount/views.py:105` — `User.objects.get(email=identifier)` возбуждает
`MultipleObjectsReturned`, поскольку `email` в `AbstractUser` не уникален.
То же для `phone`.

### 25. Текстовая версия письма — каша из CSS

`signals.py:407`, `check_mass_mail_campaigns.py:182` — `strip_tags(html)`
оставляет содержимое `<style>`, склеивает соседние ячейки таблиц и теряет
адреса ссылок.

**Тесты:** `test_style_content_is_not_leaked_into_text`,
`test_adjacent_cells_are_not_glued_together`, `test_links_keep_their_target`

### 26. Поля `blocked` и `deleted` не влияют на вход

`useraccount/views.py:81-190` проверяет только `is_active`. Заблокированный
модерацией пользователь продолжает работать.

### 27. Раскрытие адресов всех пользователей

`views.py:1281-1304` — любой авторизованный пользователь получает список
email всех активных учётных записей.

### 28. Мутация объекта настроек перед отправкой

`signals.py:82-108`, `check_mass_mail_campaigns.py:42-86` — `fix_smtp_settings`
меняет поля модели («исправим порт для Beget»). Изменения могут уехать в БД
при последующем `save()` и незаметно испортить сохранённый профиль.

**Исправление:** параметры подключения собираются в неизменяемый
`SmtpCredentials`, модель не трогается.

### 29. Неполный список «строгих» провайдеров

`check_mass_mail_campaigns.py:26-32` — перечислены конкретные домены
(`smtp.yandex.ru`, `smtp.yandex.com`), поэтому `smtp.yandex.by` и
корпоративные домены на Яндексе не покрываются и получают `5.7.1`.

**Исправление:** проверка по подстроке-маркеру.

### 30. Значение `created_at` игнорируется

`check_mass_mail_campaigns.py:294-299` — в `MassMailLog.objects.create`
передаётся `created_at=timezone.now()`, но поле объявлено `auto_now_add=True`
и значение перезаписывается. Безвредно, но вводит в заблуждение.
